# Architecture

## Overview

Keyport is a deliberately small key-release service. It provides authenticated
storage and retrieval of opaque values organized into security scopes. The
server does not interpret stored values and does not possess the client-side
Key Encryption Key (KEK).

```text
Internet
   |
   v
nginx :443
   |
   v
Gunicorn :8000 (127.0.0.1 only)
   |
   v
Flask application
   |
   v
MariaDB via local Unix socket
```

## Trust separation

The intended client design separates the automation key, encrypted value, KEK,
API key, and offline recovery credential.

The automation key is encrypted locally; only the resulting opaque value is
stored by Keyport. The KEK remains on the client.

## Scopes

A scope is the primary administrative and authorization boundary. Each scope
has a unique name, state, `lock_on_source_mismatch` setting, credentials,
allowed sources, and stored keys.

Valid states are `ACTIVE`, `LOCKED`, and `DISABLED`. Only an `ACTIVE` scope
can authorize key operations.

## Credentials

Credentials belong to scopes. The plaintext API key is generated by the
administration CLI and displayed only at creation.

The database stores `SHA-256(API key)` as a 32-byte binary value. Multiple
credentials may belong to one scope.

## Sources

Each scope has an IPv4/IPv6 source allow-list. Entries may be individual
addresses or CIDR networks.

In the reference deployment nginx overwrites `X-Keyport-Source-IP` with
`$remote_addr`, so the application does not trust a client-supplied value for
this header.

## Keys

A stored key consists of a scope, key name, and opaque key value. Keyport does
not know whether the value represents a disk key, application secret,
encrypted token, or another data type.

Authenticated clients may list key names in their scope. Listing does not
return stored key values. A scope may contain at most 1000 keys.

## Authorization flow

Conceptually, a key request:

1. validates the scope and, when applicable, the key name;
2. determines the source address;
3. parses and hashes the Bearer credential;
4. locates the credential and associated scope;
5. requires an active scope;
6. checks the source allow-list;
7. performs the requested key operation;
8. writes an audit record.

A valid credential presented from an unexpected source can optionally
transition the scope from `ACTIVE` to `LOCKED`.

An invalid random credential does not lock a scope.

## Database

The MariaDB application schema contains:

```text
scopes
credentials
sources
keys
audit
```

Scope deletion cascades to associated application records.

The database also contains:

```text
schema_migrations
```

which is deployment metadata used by the server updater rather than part of
the key storage model.

`schema_migrations` records the filename and SHA-256 checksum of every applied
database migration.

The complete schema for a new installation is maintained in:

```text
server/sql/schema.sql
```

Changes to existing installations are maintained as ordered migration files
under:

```text
server/sql/migrations/
```

Previously applied migration files are immutable. The updater compares their
current SHA-256 checksums with the values recorded in `schema_migrations` and
stops if they differ.

Database migrations are required to remain compatible with the previously
deployed application because MariaDB DDL may perform implicit commits and is
not automatically rolled back during an application rollback.

## Administrative plane

Administrative operations are performed locally using the `keyport` CLI,
which talks directly to MariaDB through the configured local Unix socket.

There is no remote administrative HTTP API.

## Deployment model

The running server uses a deployed installation under:

```text
/opt/keyport
```

rather than running directly from a Git working copy.

The deployed application and administration trees are:

```text
/opt/keyport/app
/opt/keyport/bin
```

Local configuration and the Python environment are separate from these
managed trees.

## Update model

The server updater downloads a snapshot of the current `main` branch and
treats the repository copies of `server/app/` and `server/bin/` as the desired
state of the deployed application.

Complete trees are replaced rather than updating a fixed list of individual
files. This allows future files to be added or removed without changing the
deployment mechanism.

Before deployment, the updater validates downloaded code and migration
history. Pending database migrations are applied before the application trees
are switched.

After switching the application trees, `keyport.service` is restarted and the
local health endpoint is checked.

If the new application fails to start or fails its health check, the previous
`app/` and `bin/` trees are restored. Applied database migrations are not
automatically reverted, which is why migrations must remain compatible with
the previous application version.

The updater itself is replaced only after the updated application has passed
the health check.

Infrastructure-specific configuration remains outside automatic updates. In
particular, the updater does not modify `keyport.conf`, the Python virtual
environment, systemd, nginx, Fail2ban, or TLS configuration.
